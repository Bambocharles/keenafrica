# Messaging (Session 09)

The ONE canonical Conversation/Message system for the whole platform
(`PLATFORM_CONTEXT.md`'s "Shared communication rule") — Teacher, Student,
and Admin all consume this same module (`src/lib/messaging.ts`) rather than
each owning a parallel inbox table, per `CLAUDE_BUILD_RULES.md` §3.

This session does NOT build email/push delivery — it only emits
`MessageReceived` (already typed since Session 01) for whichever future
session owns Notifications (Session 10) to consume. See "Handoff to
Notifications" below.

## Data model

- `Conversation` — `type` (`direct` | `group` | `cohort_broadcast`),
  `contextCohortId` (set only for `cohort_broadcast`), `createdBy`,
  `lastMessageAt` (bumped on every new message, drives inbox ordering).
- `ConversationParticipant` — the fixed participant set, one row per
  member. `lastReadAt` drives per-participant unread counts, computed at
  read time (no stored/cached derived state, same spirit as Session 08's
  mastery calculation). **The participant set is fixed at creation time —
  there is no add/remove-participant-later feature.**
- `Message` — `body`, `senderId`, `sentAt`. Append-only (no
  UPDATE/DELETE RLS policy at all, same shape as `lesson_versions`/
  `audit_events`) — messages cannot be edited or deleted once sent.

Attachments reuse Session 13's Asset/File service via a new `message`
`AssetEntityType` value — never a parallel attachment mechanism. A message
carries **at most one** attachment (`AssetAttachment`'s pre-existing
`@@unique([entityType, entityId])` constraint, unchanged).

## Who can message whom

`src/lib/messaging.ts`'s `assertCanMessage(actor, targetUserId)`:

1. **`messages.admin`** (ADMIN/SUPER_ADMIN by default) bypasses the
   relationship check entirely — "Admin → permitted users."
2. Otherwise the actor must hold **`messages.send`** (TEACHER/STUDENT by
   default) AND `haveSharedCohortRelationship()` must find a real
   relationship, computed fresh from Session 04's canonical
   `CohortTeacher`/`Enrollment` tables (never a duplicated relationship
   table):
   - actor teaches a cohort the target is actively/recently enrolled in
     ("Teacher → student"), OR
   - target teaches a cohort the actor is enrolled in ("Student →
     teacher"), OR
   - actor and target share an active/recently-completed enrollment in the
     same cohort ("Student → permitted student" — a classmate).

A `cohort_broadcast` instead requires the actor to hold a `cohort_teachers`
row for that specific cohort (`isCohortTeacher()`); the participant set is
snapshotted from that cohort's actively-enrolled students at
conversation-creation time — a student who enrolls afterward is not
retroactively added (see Known limitations).

### RLS widening this required (messaging_cohort_visibility migration)

Before this session, a plain STUDENT could not read `cohort_teachers` rows
for their own cohort, nor `enrollments` rows for a classmate — both tables'
SELECT policies were self(teacher)/self(student)/teacher-of-that-
cohort/`courses.manage` only. The `messaging_cohort_visibility` migration
additively widens both so `assertCanMessage()`/`listMessageableForStudent()`
can run entirely under the **acting student's own RLS context** — no
"system bypass" context was invented for this. This is a read-visibility
extension only; the underlying `CohortTeacher`/`Enrollment` rows remain
Session 04's canonical data. A classmate seeing "this student is enrolled
in this cohort" (no grades, no other PII) is the same information a real
classroom roster already exposes.

## RLS recursion — read this before touching any messaging policy

A SELECT policy that lets a participant see *other* participants' rows in
`conversation_participants` needs to check "is there ANY row in this same
table matching (conversation_id, me)" — a **self-referencing subquery on
the table's own SELECT policy**. This is a well-documented Postgres RLS
infinite-recursion trap: Postgres re-applies a table's SELECT policy to
every subquery reference to that table, including references generated by
the policy's own rewrite, and a naive self-reference never bottoms out
("infinite recursion detected in policy," Postgres error 42P17) — the same
failure class Sessions 08 (`assessments_select` ↔
`assessment_assignments_select`) and 13 (`assets_select` ↔
`asset_attachments_select`) hit as two-table cycles, just triggered here by
ONE table referencing itself.

Fix: `app_current_user_conversation_ids()`, a `SECURITY DEFINER SQL`
function that runs as the migrator/table-owner role (bypasses RLS entirely,
same as any owner-run query) and is therefore **opaque to the RLS
rewriter** — referencing it from a policy never re-triggers
`conversation_participants`' own SELECT policy. `SET search_path = public`
pins it against search-path injection (a real `SECURITY DEFINER` footgun),
per `CLAUDE_BUILD_RULES.md` §6. The same pattern
(`app_current_user_enrolled_cohort_ids()`) fixes the equivalent trap in the
`messaging_cohort_visibility` migration.

**If you extend any of these policies: never add a raw subquery from a
table's SELECT policy back into itself, or into a table whose own SELECT
policy subqueries back into the first — always go through one of these
functions, or a genuinely new one, instead.**
`src/lib/messaging-rls.integration.test.ts` is what actually proved this —
run it (`RLS_TEST_DATABASE_URL` set) after touching any of these policies.

## Migrations

- `messaging_core` — `Conversation`/`ConversationParticipant`/`Message`
  tables + RLS, `ConversationType` enum, reserves the `message`
  `AssetEntityType` value (does NOT use it yet — see next migration).
- `messaging_asset_attachments` — a **separate** migration adding the
  `asset_attachments` RLS branches that reference `'message'`. Split out
  because Postgres cannot use a newly added enum value in the same
  transaction that added it (each migration file is its own transaction).
- `messaging_cohort_visibility` — additive widening of
  `cohort_teachers_select`/`enrollments_select` (see above).

## APIs/contracts (`src/lib/messaging.ts`)

- `assertCanMessage(actor, targetUserId)` — throws `AuthorizationError`.
- `startConversation({ type, participantIds?, cohortId?, body, attachment? }, actor)`
  → `{ conversation, message }`.
- `sendMessage(conversationId, { body, attachment? }, actor)` — requires
  actor already be a participant.
- `markConversationRead(conversationId, actor)`.
- `listMyConversations(actor)` → `ConversationSummary[]` (with
  `unreadCount`, most-recent-first).
- `getConversationThread(conversationId, actor)` → full message list +
  participant list. Requires participant membership.
- `listMyBroadcastCohorts(actor)` / `listMessageableStudentsForTeacher(actor)`
  / `listMessageableForStudent(actor)` — compose-screen recipient pickers.

## The `MessageReceived` event contract (for Notifications, Session 10)

Already typed in `src/lib/events.ts` since Session 01:

```ts
MessageReceived: { messageId: string; conversationId: string; recipientId: string };
```

Emitted **once per OTHER participant** (never the sender) from both
`startConversation()` and `sendMessage()` — a 3-person group message emits
2 events, one per non-sending recipient. A listener should re-fetch the
message/conversation under its own RLS context using these ids (never
assume the payload alone is enough context, per `events.ts`'s own payload
discipline) — call `getConversationThread(conversationId, actor)` scoped to
the recipient to render a real preview.

This session emits the event; it deliberately does NOT send email/push
(`sessions/09-messaging.md`'s "Must NOT" list) — that is entirely Session
10's scope.

## Permissions

Two new keys, both extending `src/lib/authz.ts`'s existing
`PERMISSIONS`/`DEFAULT_ROLE_PERMISSIONS` — no parallel permission
mechanism:

- `messages.send` — TEACHER, STUDENT by default. Necessary but not
  sufficient; see "Who can message whom" above.
- `messages.admin` — ADMIN, SUPER_ADMIN by default (via
  `ALL_PERMISSION_KEYS`). Bypasses the relationship check.

## UI

- `teacher.<domain>/messages`, `.../messages/new`, `.../messages/[id]` —
  message a student, a selected group, or broadcast to a cohort.
- `student.<domain>/messages`, `.../messages/new`, `.../messages/[id]` —
  message a teacher or a classmate.
- `admin.<domain>/messages`, `.../messages/new`, `.../messages/[id]` —
  search any user (reuses `src/lib/users.ts`'s existing `listUsers()`, no
  new user-search logic) and message them; gated on `messages.admin` in
  both the nav (`showMessages` in `NavLinks.tsx`) and each page.

All three portals' index/new/thread pages check
`isFeatureEnabled(FEATURE_FLAGS.MESSAGING)` (seeded off by default, per
`PLATFORM_ARCHITECTURE.md` §12) and show a "not yet turned on" banner
instead of the real inbox when disabled — an admin flips it on from
`/flags`. This is a rollout switch, not a security boundary: every
Server Action still goes through the same `assertCanMessage`/participant
checks regardless of the flag, matching how every other flag in this
repo behaves today.

## Extending this for a new consumer (Sponsor/Certificates, Sessions 11/14)

Reuse this module directly (`startConversation`/`sendMessage` don't care
which portal calls them) rather than building a parallel system. If a new
actor type needs a new relationship rule (e.g. "Sponsor → their project's
beneficiary"), add a new branch to `assertCanMessage()` — never a second
authorization function for the same Conversation/Message tables.

## Known limitations

- **No add/remove participant after creation.** The set is fixed at
  `startConversation()` time. A `cohort_broadcast`'s participant list is a
  snapshot — a student enrolled into that cohort afterward is not
  retroactively added to that conversation (they'll receive future
  broadcasts started after their enrollment).
- **No message edit/delete.** Append-only by design (see Data model).
- **No block/report/moderation UI.** `sessions/09-messaging.md` lists
  "moderation/report/block controls" under "Owns" with "where
  appropriate," but it is not in the Acceptance criteria list. Deliberately
  deferred rather than half-built — add a `UserBlock`-style table and a
  check in `assertCanMessage()`/`sendMessage()` if a future session needs
  it; no schema decision here blocks that.
- **No group conversation for students**, only direct (teacher/classmate).
  Not required by `sessions/09-messaging.md`'s use-case list; `startConversation`
  itself has no such restriction (a "group" type works for any actor that
  passes `assertCanMessage` against every target) — only the Student
  portal's compose UI doesn't offer it.
- **Attachments buffer fully into memory** — same limitation Session 13
  already documented for the underlying Asset service; unchanged here.
